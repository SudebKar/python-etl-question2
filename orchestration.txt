Why this structure works (and won’t collapse later)
1️⃣ core/ – Infrastructure, not business logic

This is where APScheduler lives.

scheduler.py
→ start / stop APScheduler, graceful shutdown

registry.py
→ reads DB schedule metadata and registers jobs

locks.py
→ ensures only one scheduler instance fires jobs in OCP

This avoids duplicate triggers when pods scale.

2️⃣ jobs/ – Trigger logic only

These are thin wrappers.

time_based.py

Cron → call trigger_service

event_based.py

Poll run_state table

Detect completion

Fire dependent process

No ETL logic. No metadata interpretation.

3️⃣ models/ – DB is the source of truth

These mirror tables like:

schedule configuration

process run state

dependencies

This is what replaces Autosys job definitions.

4️⃣ services/ – The brain

This is where orchestration decisions happen:

Should this job fire now?

Has it already fired?

Was it retried?

Was dependency satisfied?

This keeps jobs/ dumb and testable.

5️⃣ repository/ – Isolation from DB tech

Tomorrow:

SQL Server → Postgres

On-prem → cloud

Your scheduler logic doesn’t care.

6️⃣ main.py – One responsibility
Start scheduler
Load schedules
Run forever


No HTTP server. No UI. No FastAPI.
